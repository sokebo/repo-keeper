# repo-keeper

> **占位名，随时改。**
>
> 对 GitHub 仓库做整套建模，让用户看清**自己到底做了什么**、**这些事怎么串起来**。
>
> 类比：**仓库管理员** —— 替仓库主理清全貌。

---

## 一、四步目标（顺序不可换）

1. **验证 & 迭代优化 kael**
2. **解决自己的痛点**
3. **开源，开始积攒 star**
4. **解决其他人的痛点**

第 1 步排在第 4 步之前：**先自己用起来、把发动机验证了，再谈服务别人。**

> 顺带说明：`ekko` 是 kael 的第一个验证场，`repo-keeper` 是第二个。
> 前者验证的是"证据层能不能不误杀"，后者验证的是"结构推理层有没有用"。

## 二、它解决什么痛点

痛点已经被观察证实，不是推演：

> 团队述职前要做 PPT，大家开始用 Codex 去仓库"猛猛拉"自己过去的工作内容。

这个现象说明三件事：

1. **痛点真实** —— 每年都要做，躲不掉
2. **现在靠 AI 硬扛** —— 慢、每次说法不一样、隐私出本机、下次从零重来
3. **有捷径的人是"懒"** —— 自己手动找太花时间。连作者本人也会选择用 Codex

## 三、它不是什么（防跑偏用）

| 不是 | 因为 |
|---|---|
| GitHub 数据导出器 | commit→PR、PR→issue、milestone 这些 GitHub 原生就有，不重复造 |
| **述职工具** | 述职是最容易感知到痛的时刻，但**不是产品定义**。把入口当定位会做歪 |
| 图可视化工具 | **图是中间产物**。GitHub 贡献热力图就是最好的反例：全球知名，但没人为它装工具 |
| 取代 AI 的东西 | **连作者本人都会绕过它去用 Codex**。定位成"替代 AI"从第一天就输了 |

## 四、节点与边

### GitHub 原生就有（不重复造）

- commit → branch → PR
- PR → issue（closing keywords `fixes #123`）
- issue → milestone / label / project
- review 关系、共同 reviewer

### 要算的（三类）

1. **commit / PR ↔ 决策文档**
   GitHub 只索引 commit message、PR 描述、issue 正文，**不索引仓库里的 markdown**。
   `notes/01-decisions/决策日志.md` 这类文件在 GitHub 上一条都搜不到。

2. **issue ↔ issue 是否同一话题**

3. **PR ↔ PR 是否同一主线**

## 五、查询清单（管理员视角）

| 问题 | Codex 能不能给 | 为什么 |
|---|---|---|
| 我最近在忙什么 | 能，但每次说法不一样 | 无状态 |
| 这些事怎么串起来 | 部分能 | 无状态 |
| **哪些 issue / PR 挂着没人管** | ❌ | 不知道历史 |
| **哪些分支僵尸了** | ❌ | 不知道上次跑到哪 |
| **有没有重复 issue** | ❌ | 要全库对比，不是问一句 |
| **决策落档了但没落地** | ❌ | 文档和 commit 之间的对应关系得有人接 |

**后四类全都需要一套持续维护的模型。** 这就是"建模"而不是"生成报告"的原因——
**报告是一次性的，建模是长期的。**

## 六、形态主张

- **本地跑。** 数据不出本机。
- **复用 `gh auth login`**（device flow，**不需要自建 OAuth 服务器**）。`gh` CLI 已经有了。
- **可查，不只出报告。** 建模如果不能查，就只是一堆数据。

### 隐私边界怎么划

不能一边说"全本地"、一边把数据喂给 Codex 写 PPT。精确的说法是：

> **commit / issue 正文从不离开本机。出本机的只有聚合后的结论。**

这不是妥协，比"全本地"更强，因为它具体。

## 七、怎么验证 kael（第 1 步目标的兑现方式）

**对照组**：只用 GitHub 原生的 label / milestone 分组做聚类。

拿 kael 的结果和它比：

| 结果 | 结论 |
|---|---|
| 差不多 | **kael 没用**，省下大量时间 |
| 明显更好 | **这就是 kael 的证据**，而且是有对照的证据 |

这不是"先不用 kael"，是**给 kael 找一把尺子**。

**判据只有一条：分类精不精、排序有没有把有价值的顶上来。** 不看 UI，不看好看程度。

## 八、已知的 gap

第 3 步（开源）在第 4 步（解决别人痛点）之前，顺序是对的，但代价是：

**开源那天起，别人会拿通用需求来用，而第一版完全是为自己的仓库设计的。**

- 本人的仓有决策日志 → 别人的不一定有
- 本人的仓有 D-KR 编号规范 → 别人的不一定有
- **通用化天花板**：分层模型在"随手 commit"的仓上，第二层几乎是空的，**模型塌成单层，价值减半**

撞上这个 gap 时有两条路：**加抽象层兼容**，或**明说"第一版只支持有留档习惯的仓库"**。
倾向后者 —— 前者就是通用化，而通用化有天花板。

## 九、诚实边界

- 第 2 节的痛点**有实测观察**（团队在用 Codex 拉），但**没有统计过多少人真的痛**
- 这类工具品类不空（GitHub Insights / Sourcegraph / 各类 commit 摘要插件）
- **差异化不在"拉数据"，在第五节后四类**——那些是跨时间问题，Codex 无状态答不了
- star 不作为判断依据（见 [[Semantica 调研结论]]：事件驱动，事件过后三个月只涨 900）

## 十、还没定的

- [ ] **第一次跑没有"上次"**，跨时间对比从哪开始（手动指定起点 / 第一次只出报告）
- [ ] **只支持本人 / 小范围，还是直接开源**
