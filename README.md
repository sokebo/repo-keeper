# repo-keeper

> 对 GitHub 仓库做整套建模，让你看清**自己到底做了什么**、**这些事怎么串起来**。
>
> 全部在你本机跑。commit / issue 正文从不上传。

**状态：早期。** 仓库建模本体还没写，现在能跑的是一个测量脚本 —— 它先帮你判断
「你的仓库到底有多少可用信号」，见[下面](#现在能跑什么)。

---

## 它回答什么问题

| 你想问 | GitHub 原生能答吗 |
|---|---|
| 我最近在忙什么 | 能，但**每次说法都不一样** |
| 这些事之间怎么串起来 | 部分能，但**没有记忆** |
| **哪些 issue / PR 挂着没人管** | ❌ |
| **哪些分支僵尸了** | ❌ |
| **有没有重复的 issue / PR** | ❌ |
| **决策落档了但没落地** | ❌ |

**加粗那四行是重点。** 它们的共同点是**跨时间** —— 要记得历史上发生过什么。
问一次 AI 拿不到，因为它不记得你上次问过什么，也从不读过你的仓库全貌。

这也是它跟 commit 摘要类工具的根本区别：**报告是一次性的，建模是长期的。**

## 为什么现在只能靠硬扛

你可能会说："问 AI 不就行了？"

实际上大家已经在这么干了 —— 述职前用 AI 工具"猛猛拉"自己过去的工作内容。
这条路的问题：

- **慢**，每次从头来
- **不稳定**，同一份工作这次这么总结下次那么总结
- **隐私出本机**，正文全喂出去了
- **不累积**，这次问完，下次还得重来

repo-keeper 想做的是把这一步固化下来。

## 它不是什么

| 不是 | 为什么 |
|---|---|
| GitHub 数据导出器 | commit→PR、PR→issue、milestone 这些原生就有，不重复造 |
| **述职工具** | 述职只是最容易感知到痛的时刻，不是产品定义 |
| 图可视化工具 | **图是中间产物**。GitHub 贡献热力图就是最好的反例：全球知名，但没人为它装工具 |
| 取代 AI 的东西 | 定位成"替代 AI"从第一天就输了 |

## 隐私

> **commit / issue 正文从不离开本机。出本机的只有聚合后的结论。**

这不是"我们承诺不上传"，而是**边界划在具体数据类型上** —— 所以它可以被检查。

细节见 [PRIVACY.md](./PRIVACY.md)。

## 现在能跑什么

仓库信号测量脚本。它会告诉你，你的仓库在下面几项上是什么水平：

- PR 的 label 覆盖率
- issue / PR 的正文密度
- commit 标题的 `#编号` 引用率
- 决策文档（RFC / ADR）的命中情况
- milestone 覆盖率
- 分支信号

**为什么要先量这个**：GitHub 原生的 label / milestone 分组在不同仓上强弱差异极大 ——
实测从 0% 到 100% 都有。**不知道自己的仓落在哪，就没法判断新方法相对基线是赚是亏。**

### 跑起来

需要 `gh` CLI 并已登录（`gh auth login`）：

```bash
# 测某个账号 / 组织下的全部可见仓库
python3 scripts/measure_repo.py <user|org>

# 测指定的几个仓库
python3 scripts/measure_repo.py owner/repo1 owner/repo2

# 存成 JSON
python3 scripts/measure_repo.py <user|org> --json out.json
```

> ⚠️ **用你自己的账号跑。** 脚本开头会打印当前 token 身份。
> 如果你用的是一个只有测试数据的账号，测出来的结论没有参考价值。
