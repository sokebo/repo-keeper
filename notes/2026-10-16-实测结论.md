# 实测结论 · 2026-10-16

> 这份文档记的是**走不通的路**。
> 目的很实际：省得下一个人（包括未来的作者本人）再花一周试一遍。
>
> **语料说明**：测量对象是一组以私有仓为主的真实仓库（58 个仓、1004 个 PR、326 个 issue）。
> 全部数据在本地通过 GitHub API 取，未上传。**仓库名、组织名、账号名、内部路径一律不出现在本文。**
> 只公开方法论与聚合结果 —— 见 [PRIVACY.md](../PRIVACY.md)。

---

## 一、六项测量跑下来，最扎心的三个数字

| 测量项 | 实测 | 说明 |
|---|---|---|
| PR 引用 ADR / RFC / PRD | **0 / 1004** | 决策文档和 PR 之间**没有任何原生链接** |
| PR 带 milestone | **1%** | 可以从设计里删掉 |
| commit 标题带 `#编号` | 25% | 但**绝大部分是 GitHub 自动生成的 merge commit**，人工引用近零 |

**"编号引用"这条路彻底走不通。** 它是 GitHub 上最顺手的关联信号，
但在自己的真实仓库上，一条都没连上。

## 二、为什么"编号引用"会失败

直觉上 `RFC-0001` 这种编号应该是完美的关联键。实测拆开看是三层问题：

1. **量太少** —— 决策文档只分布在 14% 的仓里
2. **很多不在 GitHub** —— 文档在本地 wiki / 飞书 / NotIn，代码仓里什么都没有
3. **PR 从不引用** —— 即使文档就在同一个仓里，作者也不写编号

**可复用的部分**：识别"字母 + 分隔符 + 数字"的规则是通用的，
所以这套判定规则能做成工具。**不可复用的是纪律** ——
「必须写编号」是团队约定，不是技术机制，换个人群就失效。

## 三、纯 TF-IDF 聚类：单仓可行，不需要 LLM

拿一个活跃仓最近 100 个 PR，滤掉发布审批类的自动化产物（53 条），剩 47 条真实工作。

阈值 0.30 的纯 TF-IDF + 余弦相似度：

- 聚成 5 个非孤岛组，覆盖 **39/47 = 83%**，孤岛 17%
- 完全剔除作者名之后，**其中一个 12 条的组一条没变**（11 条是同一个人写的）

**结论：「看自己干了什么」这件事，纯统计方法就能做，不需要 LLM。**

踩到的坑：

- **作者名污染语料。** 30% 的标题带作者名前缀，直接进 TF-IDF 会把"同一个人写的"
  聚成"同一件事"。清掉作者名之后结果明显更干净。
- 正文没用上（53% 的 PR 有正文，但直接拼进去会稀释标题信号）。

## 四、跨仓就不行了 —— 稀有度阈值只有断崖

把范围拉到 8 个仓（同一个需求横跨 8 个仓推进，32 条 PR），跨仓关联靠
「两条 PR 共享一个够稀有的词」建边。**阈值一扫描，曲线没有可用区间，只有断崖：**

| 稀有度阈值 | 跨仓边数 | 主驱动词 |
|---|---|---|
| ≤6 | **3** | `tenant-scoped` / `header` / `multi-tenant`（各出现 2 次） |
| 7 | **22** | 其中 **19 条由单词 `multi`（出现 7 次）一词造出来** |
| 32 | 299 | `tenant`（出现 27/32）造出 297 条 → 图直接炸 |

**区分度最高的词只能连出 3 条边；能连出 22 条的档位里 86% 是一个废话词。**

根因：**整份语料只有一个主题**。任何词要么到处都是，要么中等频率，
稀有度判据在单一主题语料上必然失效。

换成连续权重（IDF）能分开一些（`multi` 权重 1.52 vs `tenant-scoped` 2.77），
但断崖只是挪了位置，没消失。

## 五、真正的解法不在打分，在归并

上面那 19 条假边不是"打分不准"造成的，是**结构**造成的：

把 32 条 PR 的标题归一化（去掉 `feat:` 前缀、作者名 handle、标点）之后，
**只剩 24 组，其中 4 组是重复标题，涉及 12/32 = 38% 的 PR。**

最大的一组：**同一个功能标题在 5 个仓各开了一条 PR，横跨 18 天。**

**那不是 19 条关联，是 1 件事。** 打分模型修不了这个 ——
因为问题不是"边该不该连"，是"这一组节点本来就是同一个东西"。

**所以造边的顺序必须是：先归并重复标题，再建边。**

副产品也很实在：同仓同日的重复标题，大概率是**重复提 PR**（同一个改动提了两次）。

## 六、几条会影响设计的实测

**决策文档能不能当主干？不能。** 覆盖率约 3%，样本太少，统计上撑不住。

**时间邻近能不能替代 label？不能。** 加权中位数：时间邻近 29 天 vs label 31 天，
比值 0.94 —— **时间只是 label 的近似，没有增量信息**。
这条直接否掉了一个看起来很合理的方案。

**分支信号能不能用？基本不能。** 分支名被 `develop` / `master` 这类长期分支占据，
信噪比接近零。

**作者信号强但无语义。** 头部作者贡献占比高达 85-94%，
但"谁写的"跟"这是什么事"没有映射关系。

**分层模型成立但偏薄。** 公开项目的 issue/PR 正文密度是 94-99%，
私有仓只有 53-56%。第二层（依据信息）在一半的仓里是空的，
所以"依据信息层级标记"是**必需字段**，不是可选增强。

## 七、这些结论怎么用

**能复用的（通用方法）：**

- 六项测量的口径和脚本 → [`scripts/measure_repo.py`](../scripts/measure_repo.py)
- 「字母 + 分隔符 + 数字」识别决策文档编号
- 发布审批类自动化产物的识别规则（二元可判定，可自动化）
- 重复标题归一化

**不能复用的（个人纪律）：**

- 「PR 必须引用编号」「必须有决策日志」——这是团队约定，换个人群就失效

**一条元结论：**

> 判据是**二元可判定**的（label 用没用、是不是编号、标题重不重复），
> 才值得自动化；需要判断的（哪两件事是同一件、这次改动属于什么层级）
> 应该靠人读，不该做成体检脚本。

## 八、还没测的

- 正文该怎么用（截断 / 摘要 / 单独通道）
- 重复标题归并之后，跨仓关联能不能立起来 —— **这是下一步**
- 决策文档 ↔ PR 的关联除了编号还有没有别的路
